# 游戏更新处理流程

## 输入类型

- 完整客户端或完整数据转储；
- 同版本热更新；
- 相邻版本增量包；
- 私服补齐或修正的数据；
- 解包器升级后的重新提取。

## 标准流程

1. 扫描新来源并记录原始版本字符串；
2. 创建不可变 Source Snapshot；
3. 若是增量输入，记录 base snapshot，并物化为完整来源；
4. 使用指定版本解包器生成 Extracted Snapshot；
5. 标准化并建立索引；
6. 与上一推荐快照执行文件级和语义级差分；
7. 分类影响：文本、数值、已支持原语、新原语、新 Opcode、事件顺序、AI、客户端读取布局；
8. 决定是否需要更新 Runtime Reader；
9. 决定沙箱只换 Ruleset，还是必须升级 Engine；
10. 运行跨版本黄金测试；
11. 标记受影响数据集；
12. 在新沙箱 Release 上评估现有模型；
13. 将模型标记为 `fresh`、`evaluation_required`、`stale` 或 `incompatible`；
14. 必要时重新生成数据集并训练新模型；
15. 更新 `registry/compatibility.yaml` 和别名。

## 影响判断示例

| 变化 | Reader | 沙箱引擎 | Ruleset | 模型 |
|---|---:|---:|---:|---:|
| 文本变化 | 否 | 否 | 可更新 | 否 |
| 技能倍率变化 | 否 | 通常否 | 是 | 重新评估 |
| 新角色仅使用已有原语 | 否 | 否 | 是 | 支持新角色时重训 |
| 新 Ability 原语 | 否 | 是 | 是 | 受影响范围重训 |
| 新表达式 Opcode | 否 | 是 | 是 | 重新生成相关数据 |
| 客户端内存/UI 布局变化 | 是 | 否 | 否 | 策略模型通常不变 |
| BattleState Schema 变化 | 可能 | 是/适配 | 可能 | 通常不兼容 |
