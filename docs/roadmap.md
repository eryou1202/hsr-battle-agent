# 推荐执行顺序

任务基本线性执行，但把两个决定最终产品可行性的风险尽早验证：**机制数据能否获得**和**真实客户端状态能否读取**。

## 阶段 0：建立不可推翻的骨架

执行：T00。

完成条件：

- 目录职责确定；
- Manifest 基础字段确定；
- 游戏版本、快照、沙箱、模型命名规则确定；
- 不包含任何假定的游戏字段。

## 阶段 1：打通原始数据入口

执行：T01 → T02。

目标：

```text
选择一个数据来源
→ 建立 Source Snapshot
→ 完成一次提取
→ 在研究前端看到文件、版本、Hash、错误和产物目录
```

阶段门 G1：至少有一个版本的可重复解包结果。若连稳定来源都无法获得，暂停后续沙箱工作。

## 阶段 2：建立可研究的数据

执行：T03 → T04。

目标：

```text
Extracted Snapshot
→ Normalized Snapshot
→ 角色/技能/Ability 查询
→ 两个快照的语义差分
```

阶段门 G2：输入一个角色或技能 ID，能够追踪到真实配置节点，并能识别版本变化。

## 阶段 3：尽早验证真实客户端读取

执行：T05。可在 T03 后半段开始，不必等完整沙箱。

首批只验证：

- 当前是否进入玩家决策窗口；
- 当前行动角色；
- 战技点；
- 终结技能量是否满足；
- 敌人 HP/韧性中的至少一种；
- 玩家实际选择的技能和目标中的至少一种。

阶段门 G3：连续输出带时间戳和置信度的 Runtime Trace。若正式环境只能读到很少字段，立即调整最终产品形态，不要等沙箱完成后才发现。

## 阶段 4：打穿一个真实技能

执行：T06。

目标：

```text
原始配置
→ 技能等级参数
→ 动态表达式
→ 固定木桩实验
→ 客户端每段结果
→ 独立程序计算一致
```

阶段门 G4：第一条完整数值链成立。这是沙箱是否可行的核心里程碑。

## 阶段 5：从最小沙箱扩展到完整沙箱

执行：T07 → T08。

先做：单角色、单敌人、完整行动循环。

再做：四人队、多敌人、Buff、治疗、护盾、击破、波次、终结技插队。

阶段门 G5：固定种子和固定操作序列可重复，且与客户端黄金样例达到预定一致标准。

## 阶段 6：策略规划

执行：T09。

顺序：

1. 合法动作生成；
2. 规则/Auto 基线；
3. 一步贪心；
4. Beam Search；
5. 必要时 MCTS。

阶段门 G6：同一基准集上稳定不弱于规则基线，并满足实时延迟预算。

## 阶段 7：模型

执行：T10。

顺序：

1. 搜索器生成专家轨迹；
2. Policy 行为克隆；
3. Value 估值；
4. Policy/Value 引导搜索；
5. 最后才考虑强化学习。

阶段门 G7：模型版本能追溯到数据集、沙箱 Release、特征 Schema 和评估结果。

## 阶段 8：实时顾问与最终集成

执行：T11 → T12。

T11 可提前用 Mock 状态开发界面，但正式接入放在这里。

目标：

```text
Runtime Trace
→ BattleState 重建
→ 读取置信度检查
→ Planner/Model
→ 推荐动作与备选
→ 实际结果回流
→ 偏差过大时重新规划
```

阶段门 G8：真实战斗中能够在决策窗口内稳定给出建议，并明确显示缺失字段和低置信度状态。

## 阶段 9：版本更新常态化

执行：T13，之后每次游戏更新重复。

```text
新版本快照
→ 语义差分
→ 影响分类
→ 更新读取器/沙箱（按需）
→ 跨版本黄金测试
→ 评估旧模型
→ 保留、标记 stale 或重训
```
